# Versions du bloc C et changements de comportement

> Relevé fait le 8 octobre 2026 au démarrage du bloc C (modules 12 à 18), à partir des sources officielles (dépôts APT, index Helm, canaux de k3s et RKE2, constantes de kubeadm lues au tag, notes de version, avis de sécurité). Les versions de référence sont dans [`PLAN.md`](../PLAN.md) §6. Ce fichier liste ce qui a changé récemment et qui touche les exercices : si un tutoriel plus ancien ne fonctionne plus, la raison est probablement ici. Les lignes marquées *(relecture)* ont été établies pendant la rédaction et la relecture du bloc, dans le code source des outils, les notes de version ou par des essais, et sont détaillées dans le corrigé cité.

## Conteneurs (module 12)

| Outil | Ce qui change pour toi |
|---|---|
| Docker Engine 29 (29.8, download.docker.com) | Debian 13 livre `docker.io` 26.1 : le workbook prend `docker-ce` du dépôt Docker, qui dépend de `containerd.io` (≥ 2.1.5) et de `nftables`. **Stockage d'images containerd par défaut** pour une nouvelle installation : `docker info` affiche `driver-type: io.containerd.snapshotter.v1`, les images sont sous `/var/lib/containerd` et non plus `/var/lib/docker/overlay2`, et les images multi-plateformes et leurs attestations restent en local (M12-E04). API minimale 1.44 : l'ancien binaire `docker-compose` v1 est refusé. Backend de pare-feu nftables expérimental (iptables reste le défaut). cgroup v1 déprécié. Ne pas descendre sous 29.5.2 (correctifs de `docker cp`). |
| Docker 29.8 — TCP sans TLS *(relecture)* | Contrairement à ce qu'annonce la page des fonctionnalités dépréciées, la 29.8.2 **démarre encore** avec `-H tcp://0.0.0.0:2375` sans TLS (et avec `--tls=false`) : elle journalise deux avertissements et ralentit volontairement son démarrage (≈ 15 s). Ne compte pas sur la version pour te protéger : jamais de socket en TCP, accès distant par SSH ou TLS mutuel (M12-E26). |
| Docker 29.8 — `userns-remap` *(relecture)* | Activer `userns-remap` **désactive** le stockage d'images containerd : les images déjà tirées « disparaissent » de `docker images` (elles restent dans l'autre magasin). À décider avant de remplir l'hôte (M12-E26). |
| Docker 29.8 — ports privilégiés *(relecture)* | Le démon pose `net.ipv4.ip_unprivileged_port_start=0` dans chaque conteneur : un processus non root écoute sur le port 80 même avec `--cap-drop ALL`. `CAP_NET_BIND_SERVICE` n'est plus le bon argument d'un durcissement (M12-E24, M12-E32). |
| Docker Compose v5 (5.6) | La numérotation passe de 2.40 à **5.0** (décembre 2025) ; la commande reste `docker compose` et le format de fichier ne change pas (attribut `version:` obsolète). La construction est déléguée à **Buildx / Bake** : `docker-buildx-plugin` est requis (M12-E08). |
| Compose v5 — secrets *(relecture)* | Hors Swarm, un secret de type fichier est un montage lié : `uid`, `gid` et `mode` de la déclaration sont **ignorés**. Les droits se règlent sur le fichier source (M12-E08, M12-E34). |
| Buildx 0.37 / BuildKit 0.34 | BuildKit est le constructeur par défaut depuis Engine 23 ; avec le stockage containerd, le pilote `docker` sait garder des images multi-architectures et des attestations : un constructeur `docker-container` n'est plus indispensable pour `--platform linux/amd64,linux/arm64` (M12-E12). Sans démon privilégié en CI : image `moby/buildkit:rootless`, avec les exceptions `seccomp=unconfined` et `apparmor=unconfined` écrites dans l'ADR-0120 (M12-E21). |
| Kaniko *(relecture)* | Archivé par Google en juin 2025 : plus aucun correctif. Cité comme historique, non utilisé (M12-E21). |
| containerd 2.3 LTS / runc 1.5 | `containerd.io` 2.3.x (dépôt Docker) embarque runc 1.5 et entre en conflit avec les paquets `containerd` (1.7) et `runc` (1.1) de Debian : ne mélange jamais. containerd 2.x a retiré le CRI v1alpha2, les images Docker schéma 1 et `aufs`. La 2.4 (septembre 2026) n'est pas LTS : non utilisée. |
| Podman 5.4 (Debian 13) / 5.8 (Rocky 10) | Réseau **Netavark**, réseau sans privilège **pasta** par défaut, base d'état SQLite. Installer explicitement `passt`, `uidmap` et `dbus-user-session` : ce ne sont que des *Recommends* sur Debian (M12-E02, M12-E06). Podman 6 (juin 2026) supprime CNI, iptables, slirp4netns et cgroup v1, mais n'est dans aucune des deux distributions : non retenu. |
| Quadlet 5.4 *(relecture)* | `podman quadlet install/list/rm` n'existe qu'à partir de la 5.6 : sur Debian 13, on copie les fichiers dans `~/.config/containers/systemd/` puis `systemctl --user daemon-reload`. `HealthCmd=` s'écrit en **tableau JSON** : écrit sur une ligne, la commande perd son guillemet final ; pas d'argument vide (M12-E14, M12-E30). |
| Skopeo 1.18 — `sync` *(relecture)* | Sans `--scoped`, `skopeo sync` ne garde que le **dernier** élément du nom source (`docker.io/library/debian` devient `<destination>/debian`) : deux sources de même nom s'écrasent (M12-E13). |
| Hadolint 2.15 / Dive 0.13 | Binaires épinglés par empreinte. Dive < 0.13 échoue sur les images OCI produites par Docker ≥ 25 : imposer la 0.13.1 (M12-E16). |

## Registre et chaîne d'approvisionnement (module 13)

| Outil | Ce qui change pour toi |
|---|---|
| Harbor 2.15 | **Notary et ChartMuseum supprimés** : `install.sh --with-trivy` est la seule option ; les charts se poussent en OCI (`helm push oci://…`, M17). Cache **Valkey** au lieu de Redis ; PostgreSQL intégré passé de 15 à **18** au démarrage en 2.15.2 (sauvegarder la base avant toute montée, M13-E16) ; terminologie *proxy cache* ; prise en charge du format *bundle* de Cosign 3. Trivy 0.74 embarqué dans la 2.15.3 (adaptateur 0.39). |
| Harbor 2.15.3 — GHSA-wrw5-gmvj-gf23 *(relecture)* | Le contournement par en-tête `User-Agent` est supprimé : **Cosign n'est plus exempté** de la politique « signature exigée ». Dans un projet qui l'exige, `cosign sign` et `cosign attest` sur une image encore non signée échouent en `412 Precondition Failed`. Rétablissement : `CONTENT_TRUST_LEGACY_SIGNER_PULL_ENABLED=true` dans l'environnement du conteneur `core` (aucune clé de `harbor.yml` ; `prepare` réécrit le fichier, d'où la variable `harbor_cosign_lecture_avant_signature` du rôle `harbor`, posée après chaque `prepare`). L'exemption ne vaut que pour une identité qui peut pousser dans le projet. **Aucune exemption** pour un projet qui bloque les images vulnérables : on signe après l'analyse (M13-E02, M13-E14). |
| Harbor 2.15.3 — GHSA-2phj-cp9f-qq6w | Les webhooks (et Slack) vers des adresses privées, de bouclage ou *link-local*, y compris un nom qui s'y résout, sont **bloqués** par défaut (correctif d'une SSRF). Aucun exercice du module n'en utilise ; si tu en ajoutes un vers un service du lab (M19-M21), il faut `network.allow_private_network_access: true` dans `harbor.yml` (core **et** jobservice), ce qui retire toute la protection : préfère un relais public au lab, et bloque 169.254.169.254 au niveau réseau. |
| Harbor 2.15.3 — GHSA-xq2m-cj8w-56v5 | La portée « tous les projets » d'un robot (`namespace = "*"` du fournisseur OpenTofu) se comportait en joker global et accordait `robot:update` : prise de contrôle des robots d'autres projets. Corrigé en 2.15.3. Règle du workbook : un robot « tous les projets » (`wb-checks`) ne reçoit que de la lecture, jamais d'action sur la ressource `robot` (M13-E03). Même version : GHSA-w5fq-xrhj-j7g2 (robot système avec `user:update`), GHSA-27f2-qg57-2gwg (règle d'immuabilité à plusieurs sélecteurs contournable, M13-E10). |
| Harbor 2.15.3 — réplication en poussée *(relecture)* | Régression connue (correctif de GHSA-wjpm-hv5w-gxr6) : l'en-tête `Location` des téléversements est contrôlé plus strictement, ce qui casse la réplication en poussée vers certains registres (AWS ECR cité). Vers un Harbor, non signalé ; si les tâches échouent au téléversement des blobs avec une erreur d'en-tête `Location`, c'est elle : note-le et applique la version corrective suivante (M13-E13, M13-E16). |
| Trivy 0.75 — incident de mars 2026 (CVE-2026-33634) | Trivy **0.69.4** (binaires) et les images Docker Hub `aquasec/trivy:0.69.5` et `0.69.6` étaient malveillantes (vol des secrets des pipelines, persistance `~/.config/systemd/user/sysmon.py`) ; 76 des 77 étiquettes de `trivy-action` ont été réécrites. Versions sûres : 0.70 et suivantes. Vérification de distribution : bundle `.sigstore.json` par `cosign verify-blob --bundle … --certificate-identity …/reusable-release.yaml@refs/tags/v0.75.0`, **puis** empreinte SHA-256, puis épinglage par empreinte (M13-E05). Bases par défaut `mirror.gcr.io/aquasec/trivy-db:2` ; lab : `--db-repository` vers le cache Harbor. 0.75 retire `getHostByName` des gabarits. |
| Trivy 0.69.4 — vérification d'identité *(relecture)* | La version piégée a été **construite et signée par le pipeline officiel compromis** : `cosign verify-blob` avec l'identité attendue l'aurait **acceptée**. La signature prouve l'origine, pas l'innocuité : épinglage par empreinte, délai avant adoption d'une nouvelle version et lecture des avis restent nécessaires (M13-E05, M13-E24). |
| Cosign 3.1 | Depuis la v3 (octobre 2025) : format **bundle Sigstore** par défaut, signatures rangées comme **référents OCI 1.1** (plus d'étiquette `sha256-<empreinte>.sig`), URL des services lues dans la *signing config* TUF du *public good instance* ; `--bundle` obligatoire pour `sign-blob` ; `--tlog-upload` déprécié. Le cosign 2.5 de Debian 13 ne produit pas ces formats : imposer le binaire 3.1. Registre sans référents : `--registry-referrers-mode legacy`. |
| Cosign 3.1 — Rekor *(relecture)* | Avec une clé et **sans** configuration de signature, `cosign sign` envoie l'entrée au **Rekor public** sans rien demander (nom et empreinte de l'image publiés, définitivement). `--tlog-upload=false` est refusé avec une configuration de signature. Méthode retenue : **configuration de signature sans service** (`docs/registre/signing-config.json`, `--signing-config`) et vérification `--insecure-ignore-tlog=true` (M13-E07 ; même méthode pour les charts, M17-E08). |
| Cosign 3.1 — images multi-plateformes *(relecture)* | Signer l'index ne signe pas ses manifestes : la chaîne signe l'**index et chaque manifeste de plateforme**, après l'analyse de Harbor ; provenance attestée en type `slsaprovenance1` (M13-E08, M13-E09). |
| Syft 1.54 / Grype 0.120 | Grype : base au schéma **v6** (le v5 est en fin de vie depuis le 6 mars 2026) ; hors ligne : `grype db import`. Syft : formats `spdx-json` et `cyclonedx-json` inchangés (M13-E06). |
| Renovate 44 | Publication quasi quotidienne : épingler la majeure (`:44`) ou une version complète. Méthode GitLab : projet `renovate-runner` (v26.1.0) importé, job seulement en pipeline **planifié** ; image tirée par le cache Harbor ; jeton du compte bot en portée `api` (M13-E11). |
| policy-controller de Sigstore | Non retenu (exige Kubernetes, ferait doublon avec Kyverno au M26) : la signature est imposée par Harbor et vérifiée en CI (M13-E14). |
