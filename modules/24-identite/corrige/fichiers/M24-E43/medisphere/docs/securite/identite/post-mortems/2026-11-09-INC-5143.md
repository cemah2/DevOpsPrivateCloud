## 1. Résumé

Lundi à 07:41, `sso.par1.medisphere.internal` a répondu `503` à tout le monde : les deux répartiteurs avaient retiré `idp01` de `be_sso`, dont le contrôle de santé interrogeait le port du trafic (8443) au lieu du port de gestion (9000), où seul `/health/ready` existe. Une fois la publication rétablie (08:33), deux autres écarts sont apparus : les personnes arrivées ou modifiées depuis dimanche n'étaient plus synchronisées (le mot de passe du compte système `svc-keycloak` avait été changé dans l'annuaire seulement), et Argo CD donnait le rôle `admin` à toute personne authentifiée (`policy.default` modifié la veille). Les trois changements avaient été faits à la main, hors du code ; aucune vérification ne comparait le code et la réalité sur ces objets.

## 2. Impact

- 07:41 → 08:33 : aucune connexion SSO possible ; déploiements, diagnostics, lecture des alertes par Mailpit (`mon01:8443`) bloqués. Les rendez-vous des patients (MédiAgenda) n'ont pas été touchés.
- 08:33 → 09:05 : connexions rétablies pour les personnes déjà synchronisées ; `emma.durand` (arrivée du jour) inexistante pour les services ; nouvelles connexions parfois refusées pour les personnes dont l'entrée de l'annuaire avait changé.
- Veille 18:55 → 09:22 : toute personne authentifiée était `role:admin` dans Argo CD. Vérification faite (§3, 09:12) : 4 connexions à Argo CD dans la fenêtre (Julien, Nadia, Lucas, <MOI>), aucune action d'écriture hors des droits normaux de chacun (historique des Applications, journal d'audit du cluster).

## 4. Causes

### 4.1 Cause(s) racine(s)

1. **Publication** : contrôle de santé de `be_sso` déplacé sur 8443 (où Keycloak répond `404` à `/health/ready` puisque `http-management-port` les sert sur 9000) sur les **deux** répartiteurs : plus aucun serveur disponible, `503`.
2. **Fédération** : mot de passe de `svc-keycloak` changé dans l'annuaire seulement (rotation commencée d'un côté, RB-244 non suivi) : liaisons refusées (`err=49`), plus de synchronisation ni de lecture des groupes.
3. **Autorisation** : `policy.default: role:admin` posé à la main dans `argocd-rbac-cm` (« pour débloquer quelqu'un ») : tout utilisateur authentifié administrateur d'Argo CD.

### 4.2 Facteurs contributifs

- Trois modifications à la main la même soirée, sur trois outils, sans ticket CHG ni relecture.
- Aucune vérification planifiée de la dérive pour HAProxy, l'annuaire et Argo CD (seul le royaume en avait une, E35).
- La coupure du SSO a **masqué** l'alerte de fédération (active depuis 07:05, lue à 08:41).
- `admin.conf` utilisé la veille hors bris de glace déclaré : l'alerte `BrisDeGlaceCluster` a sonné à 18:55, sans réaction (pas d'astreinte le soir pour l'équipe `securite`).

## 5. Détection et diagnostic

| Cause | Ce qui aurait dû la signaler | Pourquoi ça n'a pas marché | Action |
|---|---|---|---|
| Publication | une alerte sur l'état des serveurs de `be_sso` vu par HAProxy | n'existait pas ; `KeycloakIndisponible` mesure `idp01:9000` directement, qui allait bien | `SsoSansServeur` (critique) ; sonde du témoin sur l'émetteur exact |
| Fédération | `FederationLdapEnEchec` | elle a sonné, mais pendant une coupure plus grave, sans regroupement ni rappel distinct | inhibition inverse proscrite ; rappel de l'alerte après le retour du SSO dans RB-246 §C |
| Argo CD | `ConfigurationArgoCDModifiee` (E39) et `BrisDeGlaceCluster` | la première n'existait pas encore dans cette version ; la seconde est arrivée le soir à `securite@`, lue le lendemain | contrôle de dérive `helmfile diff` planifié ; route de `BrisDeGlace*` vers l'astreinte aussi |

Ce qui a ralenti le diagnostic : 10 minutes passées sur Keycloak (`systemctl restart keycloak` évité de justesse : `/health/ready` était `UP`), avant de regarder le journal de HAProxy. **Réflexion transverse** : une dérive du code n'est vue par personne tant qu'aucune vérification planifiée ne compare le code et la réalité ; nous en avions une pour le royaume seulement.

## 6. Ce qui a bien fonctionné

- Les accès de secours n'ont pas été nécessaires : session `admin` sur `idp01` et `lb01`, rôles Ansible joués depuis `adm01`, sans dépendre du SSO.
- RB-246 §8 : le tableau a donné la bonne couche en une commande (raison du retrait dans HAProxy).
- La revue de la fenêtre d'Argo CD a pu se faire grâce au journal d'audit du cluster et aux événements de Keycloak (Loki `audit`).

## 8. Enseignements

- Un `503` de HAProxy ne dit rien de l'état de Keycloak : c'est le contrôle de santé qui décide.
- Une panne majeure cache les pannes mineures : après le retour du service, rejouer **toutes** les vérifications, pas seulement celle du symptôme initial.
- Les droits trop larges ne génèrent aucun ticket : il faut les chercher.
