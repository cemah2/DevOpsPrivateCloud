# docs/astreinte.md — EXTRAIT : section « Cloud OpenStack (ms-verif-openstack) » (M10-E26)

> Chaque ligne `KO` de la sonde, ce qu'il faut regarder **en premier**, et où continuer. Les commandes `openstack` se lancent depuis `adm01` avec `--os-cloud medisphere-admin` ; les commandes `docker` sur le nœud cité, en `sudo`. Journaux des services : `/var/log/kolla/<service>/` sur le nœud.

| Ligne `KO` | Premier réflexe | Journaux | Suite |
|---|---|---|---|
| `keystone aucun jeton` | `curl -sI https://openstack.par1.medisphere.internal:5000/v3` : répond-il ? Si non : `docker ps` sur `osctl01` (`haproxy`, `keystone`) ; si oui : identifiant d'application expiré ou supprimé (`openstack application credential list` en `svc-supervision`) | `keystone/keystone-apache-*.log`, `haproxy/` (via `docker logs haproxy`) | RB des pannes d'authentification (palier 4) |
| `calcul … activé mais « down »` | `docker ps --filter name=nova_compute` sur le calcul ; `docker logs --tail 50 nova_compute` ; RabbitMQ sur `osctl01` (`docker exec rabbitmq rabbitmqctl list_connections` : le calcul est-il connecté ?) ; horloge du calcul (`chronyc tracking`) | `nova/nova-compute.log` (calcul), `rabbitmq/` (contrôleur) | Redémarrer `nova_compute` seulement après avoir compris ; RB-102 si le calcul doit être vidé |
| `calcul … désactivé SANS raison` | Qui l'a désactivé ? (`openstack compute service list --long`, historique des changements) ; si c'est une maintenance : remettre une raison (`--disable-reason`) ; sinon réactiver | — | Rappeler la règle : jamais de désactivation sans référence de ticket |
| `calcul aucun nova-compute enregistré pour …` | Le nœud a-t-il été retiré (RB-102) ? Sinon, conteneur absent : `kolla-ansible deploy --limit` du calcul | `nova/nova-compute.log` | RB-102 (réintégration) |
| `reseau … mort` | Agent OVN Controller : `docker ps --filter name=ovn_controller` sur l'hôte ; agent de métadonnées : `neutron_ovn_metadata_agent` ; base Sud joignable depuis l'hôte (port 6642 de `osctl01`, ou relais 1664x) | `openvswitch/ovn-controller.log`, `neutron/neutron-ovn-metadata-agent.log` | RB des pannes réseau (palier 4) |
| `reseau aucun châssis passerelle OVN` | `osctl01` : `ovn_controller` et `openvswitch_vswitchd` en service ? `br-ex` et `ens21` (`docker exec openvswitch_vswitchd ovs-vsctl show`) | `openvswitch/` | **Urgent** : toutes les IP flottantes sont coupées |
| `volumes … down` | `docker ps --filter name=cinder` sur `osctl01` ; Ceph joignable ? (`ceph -s` sur `ceph01`) | `cinder/cinder-volume.log`, `cinder-backup.log` | Si `HEALTH_ERR` : runbooks du M08 |
| `octavia répartiteur … ERROR/OFFLINE` | `openstack loadbalancer status show <nom>` : quel membre est en erreur ? Les instances membres répondent-elles sur leur port (depuis une instance du même réseau) ? Contrôle de santé autorisé par les groupes de sécurité ? | `octavia/octavia-api.log`, `neutron/neutron-server.log` (pilote OVN) | Prévenir l'équipe propriétaire du projet |
| `noeud … unhealthy` | `docker inspect --format '{{json .State.Health}}' <conteneur>` : sortie de la vérification de santé | `/var/log/kolla/<service>/` | Redémarrage du conteneur si la cause est comprise et transitoire |
| `noeud … arrêté(s)` | `docker ps -a` ; `docker logs <conteneur>` (code de sortie) ; un conteneur arrêté **volontairement** (maintenance) doit être documenté dans le ticket | idem | `kolla-ansible deploy-containers --limit <nœud>` si l'état voulu est « en service » |
| `noeud … /var/lib/docker occupé` | `docker system df` ; journaux (`du -sh /var/log/kolla/*`) ; sauvegardes Mariabackup accumulées (volume `mariadb_backup`, purgé par `wb-backup-socle` : a-t-il échoué ?) ; anciennes images (`kolla-ansible prune-images` **après** la clôture d'une mise à jour) | — | RB-101 (purge des images) |
| `noeud … injoignable en SSH` | Le nœud vit-il ? (`qm status 210X`, console `qm terminal`) ; clé SSH de la sonde | — | Si le nœud est mort : HA (E24), RB-102 pour un calcul |
| `certificat … expire dans moins de 10 jours` | Le renouvellement ACME de Kolla a échoué : `docker logs letsencrypt_lego` ou `/var/log/kolla/letsencrypt/letsencrypt-lego.log` sur `osctl01` ; `ca01` joignable sur 443, et les VIP joignables depuis `ca01` sur le port 80 ? | `letsencrypt/` | `securite.md` §renouvellement (E27) |
| `certificat … injoignable, chaîne non reconnue` | Le bon certificat est-il servi ? (`openssl s_client -servername …`) ; racine MédiSphère dans le magasin de `adm01` | — | idem |
